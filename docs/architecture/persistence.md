# Persistence

Nihon keeps all its data in one SQLite database per installation. Only the Express.js/TypeScript server opens it, through Prisma; the Web and macOS clients use the HTTP/JSON API and never read the file, and no auxiliary tool is part of the data path. This page describes the foundation delivered by [issue #3](https://github.com/tabiitha/niihon/issues/3): storage, connections, migrations, and snapshots. Each domain adds its own models and migrations in its own issue; the first, `accounts` ([#233](https://github.com/tabiitha/niihon/issues/233)), is described in [accounts](accounts.md#data).

## Storage

| Item | Location |
| --- | --- |
| Database | `<NIHON_DATA_DIR>/nihon.db`, with its `nihon.db-wal` and `nihon.db-shm` companions while the server runs |
| Migration snapshots | `<NIHON_DATA_DIR>/snapshots/nihon-<UTC timestamp>-<schema version>.db` |
| Instance lock | `<NIHON_DATA_DIR>/nihon-instance.lock`, see the [API server](api-server.md#single-instance-per-data-directory) |

In Docker, `NIHON_DATA_DIR` is `/data`, a named volume mounted into the API container. There is no separate database container: SQLite is a library inside the server process.

| Property | Value |
| --- | --- |
| Volume | `nihon-data` in `compose.yaml`; Docker names it `nihon_nihon-data` because the Compose project is `nihon` |
| Owner | The image's `node` user (uid 1000), which runs the server |
| Modes | The database, its WAL files, and the snapshots are `600`, and `snapshots/` is `700`: only the server's user can read them. `/data` is `700` in volumes created by this image; Docker copies the image's mode only into an empty volume, so a volume created by an earlier image keeps `755` |
| Creation | On the first `docker compose up`; the server creates `nihon.db` and applies the migrations before it listens |
| Upgrade | `docker compose up --build` replaces the container and keeps the volume; the new server migrates the database on start |
| Retention | `docker compose stop`, `down`, container re-creation, and image upgrades keep the volume. Only `docker compose down --volumes` or `docker volume rm nihon_nihon-data` delete it |

Use the named volume. A bind mount from a macOS or Windows host may not propagate the file locks that SQLite and the instance lock rely on. User backup and restore ([#112](https://github.com/tabiitha/niihon/issues/112), [#113](https://github.com/tabiitha/niihon/issues/113)) will act on this volume through the API; the migration snapshots below are not that backup workflow.

## Source Structure

| File | Responsibility | I/O |
| --- | --- | --- |
| `apps/api/prisma/schema/schema.prisma` | Generator and datasource; each module adds `<module>.prisma` beside it | None |
| `apps/api/prisma/migrations/` | Versioned SQL migrations, one folder per migration, packaged in the image | None |
| `apps/api/prisma.config.ts` | Prisma CLI configuration, for generating the client and authoring migrations only | None |
| `apps/api/prisma/create-migration.ts` | `bun run db:migration <name>`: writes the next migration from the schema | File system |
| `src/database/migrations.ts` | Loads the packaged migrations; decides which to apply, or refuses the database | File system (loading only) |
| `src/database/write-gate.ts` | Serializes writes with a bounded wait and queue | None |
| `src/database/migrator.ts` | Applies pending migrations in one transaction and takes the snapshot | SQLite, file system |
| `src/database/database.ts` | Opens the database: migration, then the reader and writer Prisma clients | SQLite |
| `src/generated/prisma/` | Prisma client generated by `bun run db:generate`; not versioned | None |

The `typecheck`, `build`, `test`, and `dev` scripts regenerate the client first, so it always matches the schema.

## Connections and Transactions

The server opens two connections with Prisma's [`@prisma/adapter-better-sqlite3`](https://www.prisma.io/docs/orm/overview/databases/sqlite) driver adapter:

| Connection | Use | Settings |
| --- | --- | --- |
| Writer | Every write, in a transaction, one at a time | `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`, busy timeout 5 s |
| Reader | Every read; opened read-only, so any write through it fails | Busy timeout 5 s |

With WAL, the reader sees only committed data and never waits for the writer. better-sqlite3 runs queries synchronously on the event loop, so more connections would not run queries in parallel; two connections bound the resources.

Modules receive the database in their `register(router, { database })` context:

```ts
const items = await database.reader.$queryRaw`SELECT ...`;          // read
await database.write(async (transaction) => {                         // write
  await transaction.item.create({ data });
});
```

| Limit | Value | Effect when exceeded |
| --- | --- | --- |
| Wait for the write turn | 5 s | `DatabaseBusyError`, answered `503 database_busy` with `Retry-After: 1`; nothing was written |
| Writes waiting at once | 64 | The next write fails immediately with `DatabaseBusyError` |
| Write transaction duration | 5 s | Prisma rolls the transaction back and the write fails |

### Concurrency and Durability

Writes queue in arrival order in the server (`write-gate.ts`) rather than retrying on SQLite locks, so a write waits at most the configured delay. Keep transactions short: do the computation before `write`, and never wait for the network or the user inside one. `synchronous=FULL` makes every committed write durable before `write` resolves, which favors keeping answers over write throughput. Integrity rules belong in the schema (primary keys, unique indexes, foreign keys, `NOT NULL`); SQLite enforces them on every write, and a violation rolls the whole transaction back.

On shutdown, the server stops accepting requests, then refuses new writes, lets the running write finish, and closes both connections before releasing the data directory.

### Bounded Resources

Collections that grow are read by pages with the contract's [cursor pagination](api-contract.md#pagination), never loaded whole. SQLite's page cache keeps better-sqlite3's default of at most 16 MiB per connection, so 32 MiB for both; tune it after measurement. better-sqlite3 cannot interrupt a running statement, so long reads are bounded by pagination rather than cancelled. A migration is never interrupted midway: the whole run commits or rolls back as one transaction.

## Migrations

### Writing a Migration

1. Add or change models in `apps/api/prisma/schema/<module>.prisma`.
2. Run `bun run db:migration <name>` (lowercase, digits, underscores). It runs `prisma migrate diff` from the existing migrations to the schema, against a temporary shadow database, and writes `prisma/migrations/<UTC timestamp>_<name>/migration.sql`.
3. Review the SQL, adapt data transformations if needed, and commit it with the schema change. A committed migration is never edited.
4. Before merging, check that no migration with a later timestamp reached `main` meanwhile. If one did, delete yours, update the branch, and write it again: a database that already has the later migration would refuse a release whose history places an unapplied migration before it (`out_of_order`).

Do not run `prisma migrate dev`, `migrate deploy`, `db push`, or `migrate reset`: they would open the live database and keep their own history. The server is the only program that migrates the database.

A migration must not contain `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `RELEASE`, or `VACUUM` statements; the server refuses to start with such a migration, because it runs each migration inside its own transaction. The table redefinitions Prisma generates for SQLite (copying into `new_<Table>` with `PRAGMA foreign_keys=OFF`) work as generated.

### Applying Migrations

On every start, after claiming the data directory and before listening, the server:

1. Reads the history in the `nihon_schema_migrations` table (name, SHA-256 checksum of the SQL, application time).
2. Compares it with the packaged migrations. The history must be an unchanged prefix of the packaged list; otherwise the database is refused untouched (below).
3. Returns immediately when nothing is pending: a restart reapplies nothing.
4. Otherwise, takes a snapshot when the database already holds a schema, then applies every pending migration and its history row in **one** `BEGIN IMMEDIATE` transaction, with foreign keys checked by `PRAGMA foreign_key_check` before `COMMIT`.

`GET /api/health` only answers once this has succeeded, so a client never reaches a server with an outdated schema.

| Outcome | Log event | Exit code | Database |
| --- | --- | --- | --- |
| Migrated | `database.migrated` (applied names, `schemaVersion`, snapshot path) | Server runs | At the packaged schema |
| A migration or the snapshot failed | `database.migration_failed` (migration, or null for the snapshot; SQLite message) | 5 | Rolled back: exactly as before the start, at the previous release's schema |
| Migrated by a newer release | `database.incompatible`, `reason: "newer"` | 4 | Untouched |
| A packaged migration differs from the applied one | `database.incompatible`, `reason: "modified"` | 4 | Untouched |
| History skips a packaged migration | `database.incompatible`, `reason: "out_of_order"` | 4 | Untouched |
| SQLite file not created by Nihon | `database.incompatible`, `reason: "unrecognized"` | 4 | Untouched, not even switched to WAL |

After exit code 5, the previous release still runs on the same data; reinstall it, or fix the migration and start again. Compose restarts the container (`restart: unless-stopped`), so a failing migration is retried on each start; every attempt leaves the database unchanged and keeps the existing snapshots. Stop it with `docker compose stop` while you decide. After exit code 4 with `newer`, install that newer release, or restore a snapshot taken before the upgrade.

### Snapshots

Before applying migrations to a database that already has a schema, the server writes a consistent copy with SQLite's `VACUUM INTO`, which reads one transaction even while WAL frames are pending. The copy is written to a `.partial` file, synced to disk, then renamed, so an interrupted snapshot never looks complete; leftover `.partial` files are deleted after the next successful migration. A snapshot that cannot be written aborts the start before any migration. When the migration fails, the rollback leaves the database as it was, so the snapshot of that attempt is deleted; repeated failures therefore never push older snapshots out. After a successful migration, the three most recent snapshots are kept.

Every migration applied to an existing database is treated as potentially data-transforming, because Prisma's SQLite migrations often rebuild tables to change them. A new installation has no data, so it takes no snapshot.

To return to a snapshot, stop the server, replace `nihon.db` with the snapshot file, delete `nihon.db-wal` and `nihon.db-shm`, and start the release that matches the snapshot's schema version (its file name).

### Schema Migrations and Reference Datasets

Schema migrations change the structure of user data and travel with the server release. Reference datasets (dictionaries, kanji data, demonstration content) are versioned content with their own provenance and update cadence. They are not schema migrations: a migration never inserts literal rows (`INSERT ... VALUES`), which a test enforces on the packaged migrations, and copying existing rows with `INSERT ... SELECT` remains allowed. Each reference dataset is loaded and updated by the issue that owns it, through the server and its own version record, after the schema it needs has been migrated.

## Performance

Measured with `bun run --cwd apps/api bench:persistence` on the foundation, before any domain model exists, against a fixture collection table: two profiles, 10,000 entries generated before timing, three runs of 200 operations after 50 warm-up operations per operation type. Results on an Apple M4 Pro with 48 GB, macOS, Node.js 26.7.0, SQLite 3.53.2:

| Operation | p50 | p95 |
| --- | --- | --- |
| Read one entry by identifier | 0.02 ms | 0.02–0.03 ms |
| Read a page of 50 after a cursor | 0.05 ms | 0.06 ms |
| Insert one entry in a write transaction | 0.09–0.12 ms | 0.11–0.16 ms |
| Update one entry in a write transaction | 0.07–0.08 ms | 0.08–0.10 ms |

Database size 0.9 MiB; benchmark process RSS 218 MiB, most of it Prisma's query compiler. The issue's budgets are p95 ≤100 ms for reads and ≤200 ms for mutations. On macOS, SQLite's `fsync` does not force the drive cache to flush, so mutation timings there understate the cost of durable writes on Linux. Domain issues measure their own queries with their own data.
